# 知识缺口分析设计

## 目标

基于知识库问答中的拒答、低置信度、低证据覆盖率和用户负反馈，按最近 7 天与最近 30 天聚类出反复出现的知识主题，输出运营人员可执行的补文档建议。

## 范围与角色

- 首版只做全站汇总，不提供知识库筛选。
- 报告固定支持 7 天和 30 天两个窗口。
- 所有登录用户可查看报告；只有管理员可以手动触发分析。
- 每日凌晨自动生成两个窗口；报告生成结果持久化，页面只读取缓存。

## 数据模型

新增 `ai_answer_quality` 回答质量事实表，保存每次知识库回答的可重算输入：

- `question`、`answer_message_id`、`session_id`、`kb_id`
- `confidence`、`evidence_coverage`
- `grounded`、`refusal`、`reason`
- `create_time`

反馈通过 `answer_message_id` 关联 `ai_feedback`，查询时取该回答的最新反馈。无证据拒答和正常回答都要记录，非知识库聊天不记录。

新增 `kb_gap_report` 报告表：

- `window_days`（7 或 30，唯一）
- `sample_count`、`refusal_count`、`low_confidence_count`、`negative_feedback_count`
- `report_json`、`status`、`error_message`
- `generated_at`

报告表只保存每个窗口的最新快照，失败时保留上次成功报告并记录错误。

## 后端流程

1. `ChatService` 在知识库同步/流式回答完成后写入回答质量事实；拒答使用 `NO_EVIDENCE` 原因，正常回答写入 `AnswerEvidenceMetrics` 结果。
2. `KnowledgeGapAnalysisService` 查询窗口内事实记录，筛选以下样本：拒答、置信度低于 50、证据覆盖率低于 50、或最新反馈为无帮助。
3. 先按问题规范化去重，再调用当前激活的 OpenAI 兼容模型进行 JSON 聚类。模型输出主题、次数、代表问题、缺口判断、建议补充文档和优先级。
4. JSON 解析失败、模型不可用或样本为空时，使用可重复的规则聚类/空报告，并将错误写入报告状态，接口仍返回可展示结果。
5. `@Scheduled(cron = "0 0 3 * * *")` 每日凌晨依次生成 7 天和 30 天报告。手动触发复用同一服务逻辑，避免重复实现。

## 接口

- `GET /api/knowledge-gaps/report?days=7|30`：读取对应窗口最新报告；未生成时返回空报告和 `NOT_GENERATED` 状态。
- `POST /api/knowledge-gaps/analyze?days=7|30`：管理员触发异步分析，返回任务已提交；正在分析时返回 409。

接口统一使用现有 `Result` 包装。窗口参数只接受 7 或 30，其他值返回 400。分析过程使用单实例锁，防止定时任务与手动触发并发。

## 前端页面

新增独立 `/knowledge-gaps` 页面：

- 顶部用分段控件切换最近 7 天/30 天。
- 展示样本数、拒答数、低置信度数、无帮助反馈数、生成时间和报告状态。
- 主题列表展示主题名称、出现次数、代表问题、缺口判断、建议文档和优先级。
- 管理员显示“立即重新分析”按钮；分析中显示加载状态并轮询报告状态。
- 侧栏增加“知识缺口”入口，知识库首页增加快捷入口。

## 错误处理

- 数据库查询或 LLM 调用失败不影响聊天主流程；回答质量写入失败只记录日志。
- 报告生成失败不覆盖上次成功的 `report_json`。
- 页面请求失败显示错误提示，保留上一次已加载数据。
- 不把原始回答全文发送给 LLM，只发送去重问题、统计指标和必要的拒答原因，控制成本并降低敏感信息暴露。

## 测试

- Mapper 测试：窗口筛选、反馈关联、报告读写。
- 服务测试：样本筛选、问题去重、规则回退、JSON 解析失败、并发锁。
- 控制器测试：7/30 参数校验、读权限、管理员触发权限。
- 前端构建测试：`npm run build`；页面源码检查两个窗口切换、报告渲染和轮询清理。
- 后端回归：`mvn -B test`。
