# 智能体管理模块与知识库质检智能体设计文档

## 1. 背景

当前平台已经具备知识库管理、文件上传解析、文本分片、向量化、聊天问答、召回测试、模型配置、用量统计、文档结构化抽取等能力。下一步如果只继续堆叠单点功能，用户仍然需要自己判断知识库是否可用、分片是否合理、问答效果差的原因在哪里。

智能体管理模块的目标，是把这些已有能力组织成可运行、可复盘、可扩展的业务智能体。第一期先新增一个知识库质检智能体，用来检查 RAG 知识库从文件入库到召回问答的整体健康度。

## 2. 设计目标

第一期目标不是做复杂的多智能体编排平台，而是做一个稳定、可解释、能落地的智能体管理入口。

核心目标如下：

1. 新增一个前端菜单：智能体管理。
2. 在智能体管理中展示知识库质检智能体。
3. 支持选择知识库并运行质检。
4. 支持快速、标准、深度三种质检模式。
5. 输出知识库健康评分、风险等级、问题清单、证据明细、优化建议。
6. 保存每次质检报告，支持查看历史记录。
7. 为后续扩展更多智能体留下清晰边界。

## 3. 不做的事情

为了第一期可控，暂不做以下内容：

1. 不做复杂的多智能体协同编排。
2. 不做可视化拖拽工作流。
3. 不做定时巡检任务。
4. 不做自动修复知识库。
5. 不依赖大模型才能完成基础质检。

这些能力可以在第二期以后扩展。

## 4. 智能体与普通功能的区别

普通功能通常是用户点一个按钮，系统执行一个固定动作。例如上传文件、删除知识库、测试召回。

智能体更像一个有目标的检查员。用户给它一个目标，比如“检查这个知识库能不能上线”，它会调用多个平台能力，收集证据，判断风险，并给出下一步建议。

本模块中的知识库质检智能体具备以下特征：

1. 有明确目标：判断知识库是否健康。
2. 有输入参数：知识库、检查模式、测试问题。
3. 有执行过程：文件检查、分片检查、召回检查、覆盖检查、风险计算。
4. 有结构化输出：评分、问题、证据、建议、报告。
5. 有历史记录：每次运行都可以复盘。

## 5. 第一版智能体清单

第一版只落地一个智能体。

### 5.1 知识库质检智能体

用途：检查一个知识库是否适合用于 RAG 问答。

典型使用场景：

1. 客户上传资料后，验收知识库是否可用。
2. 问答效果不好时，定位问题来自文件、分片、召回还是知识覆盖。
3. 交付项目前，生成知识库质检报告。
4. 替换 embedding 模型或调整分片参数后，对比知识库质量变化。

## 6. 后续可扩展智能体

第一期模块边界要支持后续继续新增智能体。

后续可以扩展以下类型：

1. 文档入库智能体：自动判断文件类型、建议知识库、检查解析失败、生成标签。
2. 召回评测智能体：批量生成测试问题，评估召回命中率和证据质量。
3. 文档抽取质检智能体：检查模板字段、抽取结果、置信度、人工复核差异。
4. 合同审查智能体：基于合同知识库和抽取结果，识别风险条款和缺失条款。
5. 报告生成智能体：根据知识库和质检结果生成交付报告、周报、审查报告。
6. 平台运维智能体：检查模型配置、接口连通性、用量异常、服务健康。

## 7. 知识库质检智能体能力设计

知识库质检智能体不是只看文件数量，而是围绕 RAG 全链路设计。

### 7.1 知识库资产盘点

检查内容：

1. 知识库名称和描述是否完整。
2. 文件总数。
3. 已完成文件数。
4. 处理中或者失败文件数。
5. 文件类型分布。
6. 最近上传时间。
7. 是否存在空知识库。

输出价值：

帮助用户先判断这个知识库有没有基础可用性。

### 7.2 文件入库健康度

检查内容：

1. 上传成功但解析失败的文件。
2. 解析成功但没有分片的文件。
3. 文件大小异常小的文件。
4. 文件名重复的文件。
5. 文件名包含临时文件特征的文件。
6. 同一批资料中明显缺失的文件编号。

输出价值：

帮助用户定位文件入库链路的问题，而不是等到问答时才发现答不出来。

### 7.3 分片质量检查

检查内容：

1. 分片总数。
2. 空分片数量。
3. 过短分片数量。
4. 过长分片数量。
5. 平均分片长度。
6. 最短和最长分片长度。
7. 来源文件缺失的分片。
8. 内容重复的分片。
9. 目录、页眉、页脚、乱码、OCR 噪声片段。
10. 分片是否过度集中在少数文件。

输出价值：

帮助用户判断分片是否适合召回。分片太短会缺上下文，太长会降低召回精度，重复和噪声会污染问答。

### 7.4 知识覆盖检查

检查内容：

1. 文件名和内容是否覆盖知识库描述中的主题。
2. 是否存在大量只有标题、没有正文的资料。
3. 是否缺少 FAQ、流程、制度、条款、案例等支撑问答的材料。
4. 用户输入的测试问题是否能在知识库中找到对应主题。
5. 是否存在多个主题混在一个知识库里的情况。

输出价值：

帮助用户判断问题到底是检索能力差，还是知识库本身就缺资料。

### 7.5 召回健康检查

检查内容：

1. 使用用户填写的测试问题执行召回。
2. 如果用户未填写测试问题，基于知识库文件名和内容生成默认测试问题。
3. 检查每个问题是否有召回结果。
4. 检查召回结果是否来自多个合理文件。
5. 检查召回片段是否包含有效正文。
6. 检查召回结果是否过度集中在同一个文件。
7. 检查召回结果是否缺少来源信息。

输出价值：

帮助用户直接看到问答前的召回质量，避免把所有问题都归因到大模型。

### 7.6 问答风险判断

检查内容：

1. 知识库为空。
2. 失败文件比例过高。
3. 分片数量过少。
4. 空分片或者噪声分片比例过高。
5. 召回为空。
6. 召回证据太少。
7. 知识库主题过散。
8. 来源信息缺失。

输出价值：

把潜在问题转换成用户能理解的风险语言，例如“当前知识库不建议上线问答”。

### 7.7 优化建议生成

建议类型：

1. 重试解析失败文件。
2. 删除重复文件。
3. 补充缺失主题资料。
4. 调整分片长度。
5. 清理 OCR 噪声。
6. 补充 FAQ 或标准问答。
7. 增加测试问题集。
8. 重新向量化知识库。

输出价值：

报告不能只指出问题，还要告诉用户下一步怎么修。

## 8. 检查模式

### 8.1 快速模式

适合日常快速查看。

检查范围：

1. 文件数量和状态。
2. 分片数量。
3. 空分片、过短分片、过长分片。
4. 失败文件。
5. 基础评分。

特点：

执行快，不依赖大模型，不跑复杂召回测试。

### 8.2 标准模式

适合交付前检查。

检查范围：

1. 快速模式全部检查项。
2. 重复文件和重复分片。
3. 噪声分片。
4. 用户测试问题召回。
5. 风险等级。
6. 优化建议。

特点：

第一期默认推荐模式。

### 8.3 深度模式

适合重要知识库验收。

检查范围：

1. 标准模式全部检查项。
2. 自动生成测试问题。
3. 主题覆盖分析。
4. 召回集中度分析。
5. 更完整的上线建议。

特点：

耗时更长，可以在后续版本加入大模型总结能力。

## 9. 评分模型

评分采用 100 分制。

建议权重：

1. 文件健康度：20 分。
2. 分片质量：25 分。
3. 召回健康度：25 分。
4. 知识覆盖度：15 分。
5. 可追溯性和来源完整度：10 分。
6. 噪声与重复控制：5 分。

风险等级：

1. 85 到 100 分：健康。
2. 70 到 84 分：需关注。
3. 0 到 69 分：高风险。

扣分规则要可解释。每个扣分项都需要对应到具体问题和证据。

## 10. 报告结构

每次质检生成一份报告。

报告包含：

1. 基础信息：知识库、检查模式、运行时间、运行人。
2. 总览：评分、风险等级、摘要。
3. 指标面板：文件数、分片数、失败数、空分片数、重复数、召回问题数。
4. 问题清单：严重级别、问题类型、问题描述、证据、建议。
5. 召回测试：问题、是否命中、召回片段、来源文件。
6. 知识覆盖分析：覆盖主题、疑似缺失主题。
7. 优化建议：按优先级排序。
8. 原始 JSON：方便后续扩展和导出。

## 11. 页面设计

### 11.1 智能体管理首页

页面内容：

1. 顶部概览：已启用智能体数量、今日运行次数、待处理风险数。
2. 智能体卡片：知识库质检智能体。
3. 最近运行记录：展示最近几次质检结果。

知识库质检智能体卡片内容：

1. 智能体名称。
2. 能力说明。
3. 适用场景。
4. 最近一次运行结果。
5. 运行按钮。

### 11.2 运行质检弹窗

表单字段：

1. 选择知识库。
2. 选择检查模式。
3. 输入测试问题。
4. 是否保存报告。

测试问题支持多行输入，一行一个问题。

### 11.3 质检报告详情

页面内容：

1. 总评分。
2. 风险等级。
3. 摘要说明。
4. 关键指标。
5. 问题列表。
6. 召回测试结果。
7. 优化建议。
8. 原始报告详情。

## 12. 后端模块设计

建议新增后端包：

`com.rag.agent`

内部结构：

1. `controller`：提供智能体接口。
2. `service`：实现智能体运行逻辑。
3. `entity`：智能体运行记录。
4. `mapper`：运行记录持久化。
5. `dto`：请求和响应对象。

第一期主要服务：

1. `AgentService`：管理智能体列表、运行记录、报告详情。
2. `KnowledgeQualityAgentService`：执行知识库质检。

## 13. 接口设计

建议接口如下：

1. `GET /api/agents`
   获取智能体列表。

2. `POST /api/agents/knowledge-quality/run`
   运行知识库质检智能体。

3. `GET /api/agents/runs`
   获取智能体运行历史。

4. `GET /api/agents/runs/{id}`
   获取智能体运行详情。

5. `DELETE /api/agents/runs/{id}`
   删除运行记录。

## 14. 数据库设计

第一期可以保持简单。

建议新增表：`agent_run`

核心字段：

1. `id`：主键。
2. `agent_code`：智能体编码。
3. `agent_name`：智能体名称。
4. `run_status`：运行状态。
5. `kb_id`：知识库 ID。
6. `kb_name`：知识库名称快照。
7. `check_mode`：检查模式。
8. `score`：评分。
9. `risk_level`：风险等级。
10. `summary`：摘要。
11. `request_json`：运行参数。
12. `report_json`：完整报告。
13. `error_message`：错误信息。
14. `created_by`：运行人。
15. `created_at`：创建时间。
16. `updated_at`：更新时间。

暂不单独拆 `agent_issue` 表，因为第一期报告问题可以放在 `report_json` 中。等后续要做问题流转、确认、关闭、分配时，再拆成独立表。

## 15. 数据流

运行质检的数据流如下：

1. 用户进入智能体管理页面。
2. 前端调用智能体列表接口。
3. 用户点击知识库质检智能体。
4. 用户选择知识库、检查模式、测试问题。
5. 前端调用运行接口。
6. 后端读取知识库、文件、分片、召回能力。
7. 后端计算指标、问题、评分、建议。
8. 后端保存运行记录和报告。
9. 前端展示报告详情。

## 16. 错误处理

需要覆盖以下错误：

1. 未选择知识库：提示用户选择知识库。
2. 知识库不存在：提示知识库已删除或无权限。
3. 知识库为空：生成高风险报告，而不是直接失败。
4. 召回测试失败：保留其他检查结果，并在报告中标记召回检查失败。
5. 报告保存失败：返回明确错误，提示用户重试。
6. 后端异常：记录错误信息，运行记录状态置为失败。

## 17. 权限与安全

第一期沿用当前登录鉴权。

原则：

1. 未登录不能访问智能体接口。
2. 运行记录记录当前用户。
3. 报告中不输出模型密钥、数据库连接等敏感信息。
4. 原始分片内容展示要控制长度，避免页面过长。

## 18. 实现策略

第一期优先采用确定性规则，不强依赖大模型。

原因：

1. 质检结果更稳定。
2. 不受模型服务是否可用影响。
3. 成本更低。
4. 更容易解释扣分原因。

后续可以增加大模型增强能力：

1. 自动生成更自然的测试问题。
2. 总结知识覆盖缺口。
3. 生成面向客户的报告描述。
4. 给出更贴近业务语言的整改建议。

## 19. 测试策略

后端测试重点：

1. 空知识库能生成高风险报告。
2. 有失败文件时能生成问题项。
3. 有空分片时能扣分。
4. 有重复分片时能识别。
5. 标准模式能保存运行记录。
6. 查询历史记录能返回评分和风险等级。

前端测试重点：

1. 智能体管理菜单可进入。
2. 智能体卡片正常展示。
3. 运行弹窗能选择知识库和检查模式。
4. 运行成功后能展示报告。
5. 无数据时页面有明确空状态。

## 20. 使用说明

用户使用流程：

1. 登录平台。
2. 进入智能体管理。
3. 找到知识库质检智能体。
4. 点击运行质检。
5. 选择要检查的知识库。
6. 选择检查模式。
7. 可选输入测试问题。
8. 点击开始质检。
9. 查看评分、风险、问题、建议。
10. 根据建议处理文件、分片或知识覆盖问题。
11. 处理后再次运行质检，对比结果。

## 21. 解决的问题

该模块主要解决以下问题：

1. 知识库质量不可见。
2. 问答效果差时难以定位原因。
3. 文件解析失败容易被忽略。
4. 分片质量缺少评估。
5. 召回结果缺少验收入口。
6. 项目交付缺少可输出的质量报告。
7. 后续智能体能力没有统一入口。

## 22. 验收标准

第一期完成后，应满足以下标准：

1. 前端存在智能体管理菜单。
2. 智能体管理页面能展示知识库质检智能体。
3. 用户可以选择知识库运行质检。
4. 后端能生成结构化质检报告。
5. 报告包含评分、风险等级、问题清单、证据和建议。
6. 运行记录能保存并查询。
7. 空知识库、失败文件、异常分片等场景有明确结果。
8. 项目中存在完整说明文档，说明设计思路、使用方式和解决的问题。

## 23. 推荐实施顺序

建议实施顺序如下：

1. 新增数据库脚本和运行记录表。
2. 新增后端实体、Mapper、Service、Controller。
3. 实现知识库质检规则。
4. 新增前端 API。
5. 新增智能体管理路由和菜单。
6. 新增智能体管理页面。
7. 新增报告详情展示。
8. 编写完整功能说明文档。
9. 编译后端并构建前端。

## 24. 设计结论

第一期智能体管理模块应采用平台型智能体管理方案，而不是简单工具按钮，也不做过重的多智能体编排。

知识库质检智能体是最适合作为第一个智能体的能力，因为它直接服务于 RAG 平台最核心的质量问题。它能把文件、分片、召回、覆盖、风险和建议串起来，让用户从“凭感觉调 RAG”变成“看报告修问题”。
